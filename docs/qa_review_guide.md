# 질의응답(QA) 데이터 자동 검수 지침

> 질의응답 판정 기준의 원본. 이름에 `_QA_`가 있는 데이터만 이 지침으로 판정한다(텍스트 청크는 `review_guide.md`).
> 출처: 국가유산청 데이터 라벨링 가이드(노션) "확인 사항"의 [QA] 태그 항목 4개. 각 단계 제목 옆에 원문 번호를 적었다.
> 기준을 바꿀 때는 이 파일만 고친다. 변경 이력은 맨 아래에 남긴다.

## 원문 ([QA] 태그 항목, 노션 가이드 그대로)
- 원문①: [텍스트&QA&생성형] 요약이 본문 내용대로 썼는지 확인. 본문에 없는 사실, 연도·수치·부정문을 잘못 읽은 것, "추정된다"를 단정으로 바꾼 것이 있는지 확인 (보류 판정 후 "설명이 사실과 다름")
- 원문②: [텍스트&QA] 특정 유산에 대한 사실이 있으면 유산지식 또는 수리기록이고, 안전·공정·비용·목차처럼 유산과 관계없으면 사업관리. 사업관리는 보강 불가 처리
- 원문③: [QA] 근거 청크만으로 답할 수 있는 질문인지 확인, 답변이 질문에 직접 답하는지, 답변의 모든 사실이 근거 구간에 있는지 확인 (그렇지 않으면 보류 판정 후 "근거와 답이 불일치"를 선택)
- 원문④: [QA&생성형] 질문 유형이 맞는지 확인 (예: 수리·공사 질문에 관람정보형). 맞지 않으면 보류 판정 후 "클래스 분류 오류"를 선택

## 데이터 형식
묶음 파일의 한 줄 = 데이터 1건: {id, question, answer, question_type?, answer_type?, meta{category,difficulty,user_type}?, evidence[{doc, ctx|text}], rule_flags[...]}
- evidence의 ctx는 근거 청크 본문에서 **근거 구간을 【 】로 표시**하고 앞뒤 문맥(최대 200자)을 붙인 것이다. "…"는 청크가 더 이어진다는 표시다.
  - 【 】 안 = 근거 구간. 【 】 바깥 = 같은 근거 청크의 나머지 부분.
- ctx가 없고 text만 있으면 청크 본문을 받지 못한 것이다. text가 근거 구간 전문이다.
- ctx와 text가 함께 있으면 저장된 근거(text)와 청크 위치(【 】)가 어긋난 것이다.
- rule_flags는 scripts/prepare.py가 코드로 계산한 기계적 경고다. 참고 신호일 뿐 판정 자체가 아니다.

## 판정 값
- approve (보강가능): 아래 검사에서 문제가 없다.
- reject (보강불가): 사업관리 성격이라 학습 가치가 없다(1단계).
- hold (보류): 쓸 만한 질의응답이지만 고쳐야 할 오류가 있다.
- comment는 선택이다(프로젝트 결정: 원 가이드는 보류·보강불가 코멘트 필수). 판정 이유가 사유만으로 분명하지 않을 때만 쓴다.

## 사유 (QA에서 쓰는 것)
- "학습에 부적합한 원천" — 1단계 보강불가
- "근거와 답이 불일치" — 원문③
- "설명이 사실과 다름" — 원문①
- "클래스 분류 오류" — 원문④
reasons에는 위 문자열을 그대로 쓴다.

## 검사 순서 (1단계에서 reject면 거기서 끝낸다)

### 1. 사업관리인가 (원문②)
질문·답·근거가 다루는 사실이 특정 유산에 대한 사실(유산지식·수리기록)인지, 유산과 관계없는 사업관리인지 본다. 사업관리면 reject, "학습에 부적합한 원천".
- 텍스트 지침(review_guide.md 1단계)에서 사용자가 정한 해석을 그대로 쓴다. 아래 (가)·(나)면 사업관리가 아니다.
  - (가) 특정 유산(건물, 문, 담장, 부재, 유물 등)의 수치(치수·개수·재료·연대 등)나 형태·구조·색·문양·보존 상태. 수리 내용이라도 유산 자체의 부재·치수·훼손을 다루면 해당.
  - (나) 역사적 사실: 유산의 건립·중건·소실·수리 연도, 관련 인물·사건, 용도와 변천, 양식의 유래. 특정 유산과 무관한 조선 왕실의 제도·의례·풍습, 궁중 생활사, 역사 인물·사건, 시대별 건축 양식, 전통 기법의 유래도 포함.
- 사업관리(→ reject) 예: 안전·공정·비용·목차(원문), 공사비·공기·인원·장비, 가설·안전시설, 현대 자재 규격, 사업 일정·예산·기공식, 실측 장비와 측정 방법, 쪽번호·도면 번호·보고서 발행 정보, 회의 일정·참석자, 행정 절차, 민원·보도자료 문구.

### 보류(hold)를 내기 전 확인 (2·3·4단계 공통, 텍스트 지침 v7과 같은 프로젝트 결정)
아래 세 가지를 모두 할 수 있어야 보류다. 하나라도 못 하면 오류가 아니다(approve, 애매하면 confidence low).
1. 틀린 부분(질문, 답 문구, 근거, 질문 유형)을 그대로 짚을 수 있다.
2. 그와 어긋나는 근거 문장을 짚거나, 근거 구간·청크에 그 사실이 없음을 확인했다.
3. 그 차이가 사실(대상·연도·수치·인과·부정·추정 여부)이나 질문-답 대응을 바꾼다. 같은 뜻의 다른 표현, 세부 생략은 해당하지 않는다.

### 2. 질문·답·근거가 맞물리는가 (원문③) → hold, "근거와 답이 불일치"
세 가지를 확인한다. 하나라도 아니면 보류.
- **근거 청크만으로 답할 수 있는 질문인가.** 질문이 묻는 내용이 근거 청크(ctx 전체)에 없어서, 청크만 읽고는 답할 수 없으면 불일치다.
- **답변이 질문에 직접 답하는가.** 연도를 물었는데 위치를 답함, 두 가지를 물었는데 하나만 답함, 답이 비었거나(QA_EMPTY_ANSWER) 문장 중간에서 끊김, 질문이 비었음(QA_EMPTY_QUESTION)이면 불일치다.
- **답변의 모든 사실이 근거 구간(【 】 안)에 있는가.** 여러 근거면 근거 구간들을 합쳐서 본다.
  - 답의 사실이 【 】 바깥(같은 청크의 나머지)에만 있으면 불일치다. rule_flags의 ANSWER_NUMBER_OUTSIDE_SPAN이 강한 신호다.
  - 근거 여러 개 중 일부가 답과 무관해도, 나머지 근거 구간이 답의 모든 사실을 담으면 오류가 아니다.
- 근거 자체 문제도 여기서 본다.
  - QA_NO_EVIDENCE, EVIDENCE_EMPTY: 근거가 없다 → 불일치.
  - EVIDENCE_POS_MISMATCH: 저장된 근거(text)와 【 】 위치가 다르다. 두 쪽 모두 답의 사실을 담지 못할 때만 불일치.
  - EVIDENCE_CHUNK_MISSING, EVIDENCE_POS_MISSING: 청크 본문이나 위치를 받지 못했다. text를 근거 구간으로 보고 판정한다. 그 자체는 오류가 아니다.

### 3. 답이 근거 내용대로인가 (원문①) → hold, "설명이 사실과 다름"
원문①의 "요약"을 "답변"으로, "본문"을 "근거 청크"로 읽는다.
- 근거 청크 어디에도 없는 사실을 답에 넣음 (rule_flags의 ANSWER_NUMBER_NOT_IN_EVIDENCE 확인)
- 연도·수치를 잘못 읽음 (단위 환산·합계처럼 근거에서 바로 계산되는 값은 오류 아님)
- 부정문을 긍정으로(또는 반대로) 바꿈
- 근거의 "추정된다", "~로 보인다"를 단정으로 바꿈 (rule_flags의 EVIDENCE_HEDGED_BUT_ANSWER_NOT 확인. 추정이 붙은 사실이 답에 나오지 않으면 오류 아님)
- 2단계와 구분: 사실이 청크에는 있는데 근거 구간 밖이면 2단계("근거와 답이 불일치"), 청크에 아예 없거나 근거와 다르게 옮겼으면 3단계("설명이 사실과 다름"). 둘 다면 둘 다 쓴다.

### 4. 질문 유형이 맞는가 (원문④) → hold, "클래스 분류 오류"
- question_type이 질문 내용과 맞지 않으면 보류. 원문 예: 수리·공사에 대한 질문인데 유형이 관람정보형.
- 텍스트 지침 v7과 같이, **누가 봐도 다른 유형**일 때만 오류다. 두 유형 중 어느 쪽으로도 볼 수 있는 경계 사례는 오류가 아니다.
- question_type이 없으면 검사하지 않는다. answer_type·meta는 원문에 기준이 없으므로 검사하지 않는다.

### 5. 위 검사에 모두 통과하면 approve.
보류 사유가 여러 개면 모두 쓴다.

## 출력 형식
한 데이터에 JSON 한 줄. 필드는 아래만 쓰고, 기본값인 필드는 생략한다.
{"data_id": "...", "verdict": "approve|reject|hold", "evidence": "...", "confidence": "high|medium|low"}
- 필수: data_id, verdict, evidence, confidence.
- 묶음의 모든 건을 한 줄씩, 같은 순서로 쓴다. data_id는 묶음의 id를 그대로 옮긴다.
- reasons: reject·hold일 때만 쓴다. approve면 생략.
- comment: 선택. 사유만으로 이유가 분명하지 않을 때만 한국어 한 문장. 쓰지 않으면 필드를 생략.
- evidence: 판정의 근거가 된 질문·답·근거 부분을 짧게(50자 이내) 명사구로 적는다.
- confidence: 판단이 애매하면 low.
- 예: {"data_id":"A_QA_1","verdict":"approve","evidence":"근정전 중건 1867년, 근거 구간 일치","confidence":"high"}
- 예: {"data_id":"A_QA_2","verdict":"hold","reasons":["근거와 답이 불일치"],"evidence":"답의 월대 2단은 근거 구간 밖","confidence":"medium"}
- 예: {"data_id":"A_QA_3","verdict":"hold","reasons":["클래스 분류 오류"],"evidence":"기와 교체 질문에 관람정보형","confidence":"high"}
- 예: {"data_id":"A_QA_4","verdict":"reject","reasons":["학습에 부적합한 원천"],"evidence":"공사 기간·인원을 묻는 질문","confidence":"high"}
