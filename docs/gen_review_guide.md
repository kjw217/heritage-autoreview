# 생성형(GEN) 데이터 자동 검수 지침

> 생성형 판정 기준의 원본. 이름에 `_GEN_`이 있는 데이터만 이 지침으로 판정한다(텍스트 청크는 `review_guide.md`, 질의응답은 `qa_review_guide.md`).
> 출처: 국가유산청 데이터 라벨링 가이드(노션) "확인 사항"에서 [생성형] 태그가 붙은 항목 3개. 각 단계 제목 옆에 원문 번호를 적었다.
> 기준을 바꿀 때는 이 파일만 고친다. 변경 이력은 맨 아래에 남긴다.

## 원문 ([생성형] 태그 항목, 노션 가이드 그대로)
- 원문①: [텍스트&QA&생성형] 요약이 본문 내용대로 썼는지 확인. 본문에 없는 사실, 연도·수치·부정문을 잘못 읽은 것, "추정된다"를 단정으로 바꾼 것이 있는지 확인 (보류 판정 후 "설명이 사실과 다름")
- 원문④: [QA&생성형] 질문 유형이 맞는지 확인 (예: 수리·공사 질문에 관람정보형). 맞지 않으면 보류 판정 후 "클래스 분류 오류"를 선택
- 원문⑤: [생성형] 이미지 문항은 이미지를 직접 보고 확인. 정답이 맞고 하나뿐인지, 문항이 부재·양식·현판·주련·문양 같은 유산 요소를 묻는지 (보류 처리 후 근거는 다른 모달리티 지침과 동일)
- 참고: 사업관리 → 보강불가 항목은 [텍스트&QA]·[멀티모달] 태그에만 있다. 생성형에는 보강불가 기준이 없으므로 생성형은 approve·hold만 쓴다.

## 데이터 형식
묶음 파일의 한 줄 = 데이터 1건. 공통: {id, sub_type, content_type?, question_type?, user_type?, difficulty?, prompt, response, choices?, answer_key?, explanation?, scoring_rubric?, rule_flags[...]}
- prompt = 문항(질문) 또는 작성 요청, response = 정답 또는 생성된 문안.
- choices가 있으면 객관식 보기다. answer_key는 response와 다를 때만 있다.
- explanation·scoring_rubric = 정답 해설·채점 기준(생성 모델이 쓴 것). 판정 대상이 아니라 참고다.
- **이미지 문항 (sub_type = image_based)**: image(줄인 원천 이미지 파일 경로), image_id, image_info{place(분류 경로), title(유산명), caption(이미지 캡션)}
  - image가 없으면 이미지를 받지 못한 것이다(rule_flags의 IMAGE_FETCH_FAILED, GEN_NO_IMAGE).
  - caption은 다른 라벨러가 쓴 설명이라 틀릴 수 있다. 판정은 이미지를 기준으로 한다.
- **텍스트 문항 (sub_type = text_based)**: sources[{doc, content}] = 원천 텍스트 청크. content가 3,000자를 넘으면 잘리고 "…"로 끝난다.
- rule_flags는 scripts/prepare.py가 코드로 계산한 기계적 경고다. 참고 신호일 뿐 판정 자체가 아니다.

## 판정 값
- approve (보강가능): 아래 검사에서 문제가 없다.
- hold (보류): 쓸 만한 문항·문안이지만 고쳐야 할 오류가 있다.
- reject는 쓰지 않는다(원문에 생성형 보강불가 기준 없음).
- comment는 선택이다. 판정 이유가 사유만으로 분명하지 않을 때만 쓴다.

## 사유 (생성형에서 쓰는 것)
"보류 처리 후 근거는 다른 모달리티 지침과 동일"(원문⑤)을 아래처럼 정했다(프로젝트 가안, 사용자 확인 전).
- "설명이 사실과 다름" — 원문①, 원문⑤ 정답이 이미지와 다름
- "한자·자막 오독" — 원문⑤ 현판·주련·한자를 잘못 읽은 정답 (이미지 지침의 OCR 사유와 같음)
- "근거와 답이 불일치" — 원문⑤ 정답이 하나가 아님(맞는 보기가 둘 이상, 이미지로 정답을 정할 수 없음) (멀티모달 지침의 "사진과 문단이 맞지 않음"과 같은 쓰임)
- "학습에 부적합한 원천" — 원문⑤ 유산 요소를 묻지 않는 이미지 문항 (보류로 쓴다)
- "클래스 분류 오류" — 원문④
- "표현이 어색·불충분" — 문항·문안이 비었거나 문장 중간에서 끊김 (GEN_EMPTY_PROMPT, GEN_EMPTY_RESPONSE)
reasons에는 위 문자열을 그대로 쓴다.

## 보류(hold)를 내기 전 확인 (모든 단계 공통, 텍스트·QA 지침과 같은 프로젝트 결정)
아래 세 가지를 모두 할 수 있어야 보류다. 하나라도 못 하면 오류가 아니다(approve, 애매하면 confidence low).
1. 틀린 부분(문항, 보기, 정답, 문안 문구)을 그대로 짚을 수 있다.
2. 그와 어긋나는 것을 짚었다: 이미지에서 보이는 모습, 원천 텍스트 문장, 또는 그 사실이 원천 텍스트에 없음.
3. 그 차이가 사실(대상·연도·수치·색·형태·개수·글자·인과·부정·추정 여부)이나 문항-정답 대응을 바꾼다. 같은 뜻의 다른 표현, 세부 생략은 해당하지 않는다.
- 이미지가 작거나 흐려서 확인할 수 없는 것은 오류가 아니다(approve, confidence low).

## 이미지 문항 검사 (sub_type = image_based)
image 파일을 Read로 열어 **이미지를 직접 본다**. 이미지를 보지 않고 caption만으로 판정하지 않는다. image가 없으면 verdict "error", comment "이미지 없음".

### I-1. 유산 요소를 묻는가 (원문⑤) → hold, "학습에 부적합한 원천"
- 문항이 부재(기둥·창호·지붕·기와·계단·기단 등), 양식, 현판, 주련, 문양, 단청, 석조물처럼 **유산 자체**를 묻는지 본다.
- 하늘·날씨·나무·사람·차량·촬영 구도·사진 색감처럼 유산과 무관한 것만 묻으면 보류.
- 유산 요소를 묻되 위치·색·개수를 함께 묻는 것은 해당하지 않는다(예: "왼쪽 기둥 주련의 글씨 색").

### I-2. 정답이 이미지와 맞는가 (원문⑤) → hold, "설명이 사실과 다름" / 현판·주련 글자면 "한자·자막 오독"
- 정답(response, 객관식이면 answer_key 또는 response)이 이미지에서 보이는 것과 맞는지 본다.
- 색·형태·개수·위치·문양 이름이 이미지와 다르면 보류.
- 현판·주련 글자를 묻는 문항에서 정답 글자가 이미지와 다르면 "한자·자막 오독".
- 정답이 caption이나 해설에만 있고 이미지로는 확인되지 않는 사실(건립 연도, 용도 등)이면 I-3을 본다.

### I-3. 정답이 하나뿐인가 (원문⑤) → hold, "근거와 답이 불일치"
- 객관식: 이미지로 보아 맞는 보기가 둘 이상이면 보류. 맞는 보기가 하나도 없으면 I-2(정답이 틀림).
- 주관식: 질문이 가리키는 대상이 이미지에서 둘 이상이라 답이 갈리면(예: "기둥의 색"인데 기둥마다 색이 다름) 보류.
- 이미지만 보고는 답할 수 없는 질문(보이지 않는 내부, 연도·인물 같은 지식)이면 보류.

### I-4. 질문 유형이 맞는가 (원문④) → hold, "클래스 분류 오류"
- question_type이 객관식인데 보기가 없거나(MCQ_NO_CHOICES), 주관식인데 보기가 있으면(QTYPE_HAS_CHOICES) 보류.
- 객관식의 정답이 보기에 없거나(MCQ_ANSWER_NOT_IN_CHOICES), 보기가 중복이면(MCQ_DUPLICATE_CHOICES), answer_key와 response가 다르면(MCQ_RESPONSE_NE_ANSWER_KEY) 보류. 이 셋은 "근거와 답이 불일치"로 쓴다.

## 텍스트 문항 검사 (sub_type = text_based)

### T-1. 문안이 원천 텍스트 내용대로인가 (원문①) → hold, "설명이 사실과 다름"
원문①의 "요약"을 "문안(response)"으로, "본문"을 "원천 텍스트(sources)"로 읽는다.
- 원천 텍스트 어디에도 없는 사실을 문안에 넣음 (rule_flags의 RESPONSE_NUMBER_NOT_IN_SOURCE 확인)
- 연도·수치를 잘못 읽음 (단위 환산·합계처럼 원천에서 바로 계산되는 값은 오류 아님)
- 부정문을 긍정으로(또는 반대로) 바꿈
- 원천의 "추정된다", "~로 보인다"를 단정으로 바꿈 (rule_flags의 SOURCE_HEDGED_BUT_RESPONSE_NOT은 원천 어딘가에 추정 표현이 있다는 약한 신호다. 추정이 붙은 그 사실이 문안에 단정으로 나올 때만 오류)
- 해설문·대본·안내문의 도입·맺음 문장("~를 둘러보시기 바랍니다" 같은 안내 문구), 원천 사실을 쉽게 풀어 쓴 표현은 오류가 아니다.
- 다국어 안내문은 외국어 문안의 사실이 원천과 맞는지만 본다. 번역 문체는 판정하지 않는다.
- 원천 텍스트가 잘렸으면("…") 잘린 뒤에 있을 수 있는 사실은 오류로 보지 않는다(approve, confidence low).

### T-2. 요청 유형이 맞는가 (원문④) → hold, "클래스 분류 오류"
- content_type(해설문·오디오가이드 대본·전시패널 문구·교육자료·다국어 안내문 등)과 prompt의 요청, response의 형식이 **누가 봐도 다르면** 보류(예: 다국어 안내문인데 문안이 한국어뿐, 전시패널 문구 요청에 문답 형식).
- 어느 쪽으로도 볼 수 있는 경계 사례는 오류가 아니다. user_type·difficulty는 원문에 기준이 없으므로 검사하지 않는다.

## 공통
- GEN_EMPTY_PROMPT, GEN_EMPTY_RESPONSE, 문안이 문장 중간에서 끊김 → hold, "표현이 어색·불충분".
- 위 검사에 모두 통과하면 approve. 보류 사유가 여러 개면 모두 쓴다.

## 출력 형식
한 데이터에 JSON 한 줄. 필드는 아래만 쓰고, 기본값인 필드는 생략한다.
{"data_id": "...", "verdict": "approve|hold", "evidence": "...", "confidence": "high|medium|low"}
- 필수: data_id, verdict, evidence, confidence.
- 묶음의 모든 건을 한 줄씩, 같은 순서로 쓴다. data_id는 묶음의 id를 그대로 옮긴다.
- reasons: hold일 때만 쓴다. approve면 생략.
- comment: 선택. 사유만으로 이유가 분명하지 않을 때만 한국어 한 문장. 쓰지 않으면 필드를 생략.
- evidence: 판정의 근거(이미지에서 본 것, 원천 문장)를 짧게(50자 이내) 명사구로 적는다.
- confidence: 판단이 애매하거나 이미지에서 확인이 어려우면 low.
- 예: {"data_id":"A_GEN_1","verdict":"approve","evidence":"주련 흰 바탕 푸른 글씨, 이미지 일치","confidence":"high"}
- 예: {"data_id":"A_GEN_2","verdict":"hold","reasons":["설명이 사실과 다름"],"evidence":"정답 붉은 기둥, 이미지는 녹색 기둥","confidence":"medium"}
- 예: {"data_id":"A_GEN_3","verdict":"hold","reasons":["학습에 부적합한 원천"],"evidence":"하늘 색만 묻는 문항","confidence":"high"}
- 예: {"data_id":"A_GEN_4","verdict":"hold","reasons":["설명이 사실과 다름"],"evidence":"문안 1834년 중건, 원천은 1833년","confidence":"high"}
