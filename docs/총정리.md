# 총정리 — 국가유산 텍스트 라벨 자동 검수 (2026-10-29 대화 기준)

이 문서는 claude.ai 대화에서 진행한 내용을 VS Code의 Claude Code CLI로 이어가기 위한 인수인계 문서다.
수치는 모두 2026-10-29 15:00~15:40 KST 시점의 실측 또는 그에 근거한 추정이다.

---

## 1. 목적

- 국가유산 라벨 뷰어(https://heritage.ogqgyn.com)의 텍스트 데이터 "표본 검수"를 서브에이전트로 자동화한다.
- 구조
  - 감독(메인 세션)이 묶음을 나누고 검수 에이전트를 병렬로 돌린다.
  - 결과는 파일로 남긴다.
  - 사이트 저장은 사람이 별도로 한다.
- 실험 가동(`/pilot`)과 실제 검수(`/review`)를 분리한다.

## 2. 원천 자료

- **라벨링 가이드 (노션):** https://gynetworks.notion.site/4054b10da7888021ae99e7c95592de82
  - 텍스트 관련 원문 항목:
    - 요약이 본문대로인지: 본문에 없는 사실, 연도·수치·부정문 오독, "추정된다"의 단정화 → 보류 "설명이 사실과 다름"
    - 특정 유산 사실이면 유산지식·수리기록, 유산과 무관(안전·공정·비용·목차)이면 사업관리 → 사업관리는 보강불가
    - 엔티티 타입·관계가 본문과 맞는지: 타입 오류 → "클래스 분류 오류", 근거 문장이 다른 사실 → "근거와 답이 불일치"
  - 판정 유형:
    - 보강가능(PASS) 장당 100원
    - 보강불가(FAIL) 0원
    - 보류 5원. 원 가이드는 보류·보강불가에 코멘트 필수인데, 이 프로젝트는 사용자 지시로 선택이다.
- **세트 현황 (텍스트 16차):** 전체 5,340건 / 사람 저장 1,403건 / 미검수 3,937건 / Claude 사전 판정 0건
- **미검수 3,937건 크기**
  - 본문 총 313만 자 (중앙값 620자)
  - 요약 총 262만 자 (중앙값 727자)
  - 150자 미만 조각 106건, 한글 비율 25% 미만 330건
  - 본문이 완전히 같은 중복 23건

## 3. 사이트 API (확인된 것)

| 용도 | 요청 |
|---|---|
| 로그인 | `POST /api/auth/login` {email, password} → 세션 쿠키(HttpOnly) |
| 로그인 확인 | `GET /api/auth/me` |
| 목록 | `GET /api/labels?set=&review=pending\|human\|claude\|done&sort=data_id&order=asc&offset=&limit=` → {total, items[{data_id, verdict, verdict_by, …}]} |
| 라벨 | `GET /api/label/{id}?set=` → {label: {content, entities[{type,name,start,end}], entity_relations[{subject,predicate,object,crm,evidence{start,end,text}}], summaries{core,short,detailed,easy,educational}, material_class, topic_class, class_code_path, …}} |
| 판정 조회 | `GET /api/review/{id}?set=` |
| 판정 저장 | `POST /api/review/{id}` {set, verdict: approve\|reject\|hold, reasons[], comment} |
| 집계 | `GET /api/review-stats?set=`, `GET /api/stats?set=` |

- 사이트의 사유 목록: 설명이 사실과 다름 / 검출 영역이 부정확 / 클래스 분류 오류 / 한자·자막 오독 / 근거와 답이 불일치 / 표현이 어색·불충분 / 학습에 부적합한 원천
- **저장 기록:** `POST /api/review`로 저장하면 `by: "human"`, `reviewer: 로그인 계정`으로 기록된다.
  - 툴에는 "Claude 사전 판정"(점선 제안) 개념이 따로 있지만, 이를 쓰는 API는 확인하지 못했다.
- 라벨 뷰어 개요 페이지의 구축 원칙에 "생성·검증 모델 분리(같은 계열 모델이 자기 산출물을 판정하지 않는다)"가 있다.
  - 텍스트 라벨은 Claude_Text_Labeler가 만들었으므로, Claude 서브에이전트 검수는 이 원칙과 충돌한다. 팀 판단이 필요하다.

## 5. 판정 기준의 변천 (현재 v6)

| 버전 | 내용 | 결정 주체 |
|---|---|---|
| v1 | 노션 가이드 텍스트 항목 + 자료 분류(material_class)로 판정 | 가이드 |
| v2 | 수리기록 등 자료 분류는 판정에서 제외. 본문에 특정 유산의 수치·역사 사실이 있는지로 1단계 판정. 없으면 보강불가 | 사용자 |
| v3 | 역사적 사실은 특정 유산과 무관해도 인정 (왕실 제도·의례·풍습, 궁중 생활사, 역사 인물·사건 등) | 사용자 |
| v4 | 글 일부가 아니라 전체 내용이 기준에 맞아야 함. 코멘트 선택 | 사용자 |
| v5 | 전체 내용 기준 원칙 명시, 비수치 형태·구조·상태 묘사 인정, 실측 장비·방법 설명은 보강불가, 요약의 청크 경계 메타 문장은 오류 아님 (텍스트_CL2 시범 반영) | 사용자 |
| v6 | 수리지침·자문결과류는 역사적 사실·일화가 있으면 보강가능, 앞뒤 청크·문서 맥락 보충(대상 이름 등)은 오류 아님 (텍스트_CL2 101건 반영) | 사용자 |

- 제가 정한 세부 사항 (바꿔도 됨)
  - "전체 내용"의 수치 기준: 대략 본문 분량의 절반 이상
  - 앞뒤 청크 보충 허용: 본문이 잘려 있고 요약이 잘린 부분을 보충한 경우 오류로 보지 않고 `cross_chunk: true`로 표시. 예: JM_TXT_000035_C315 "남동쪽 599mm"
  - 대상별 요약 대조 문구: 하층/상층 혼동 오판을 줄이기 위해 v4에 추가
- 현재 지침의 3단계 구조
  1. 사실 포함 여부: 없으면 보강불가 "학습에 부적합한 원천"
  2. 엔티티·관계: 오류면 보류
  3. 5종 요약: 오류면 보류
  4. 모두 통과하면 보강가능

## 7. 비용·시간

- **실측**
  - 26건 묶음(2차): 서브에이전트 토큰 약 8.4만, 약 2분 15초 → 건당 약 3.2천 토큰
  - 13건 묶음(1차, 기본 에이전트): 약 11.3만 토큰
- **미검수 3,937건 추정 (26건 × 152묶음):** 서브에이전트 토큰 약 1,270만
  - 하네스 보고 기준이다. 도구 호출마다 대화가 다시 읽히므로 실제 처리 입력은 더 많고, 대부분 캐시 읽기다.
- **동시 실행 수별 소요 시간**

  | 동시 실행 | 소요 |
  |---|---|
  | 4개 | 약 1.5시간 |
  | 10개 | 약 45분 |
  | 20개 | 약 25분 |

- **동시 실행 한도:** Claude Code 기본 20개(`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`로 변경). 총 개수 제한은 없다.
- **요금제 사용량 %:** 계산할 수 없다. 한도가 토큰 수로 공개되지 않는다.
  - 측정법: 사용량 %를 기록 → 1개 묶음 실행 → 증가분 × 묶음 수
- **이 프로젝트에서 줄어드는 부분 (claude.ai 대화 방식 대비)**
  - 검수 에이전트가 브라우저 대신 미리 만든 묶음 파일을 Read 1회로 읽고 Write 1회로 쓴다. 도구 호출이 약 11회에서 2~3회로 줄어 재전송이 크게 준다.
  - 판정에 쓰지 않는 필드(유산 ID, CIDOC 코드, 자료 분류)를 뺐다.
  - 감독이 짧은 새 세션에서 돌고, 묶음 데이터를 직접 읽지 않는다.
  - 판정 품질에는 영향이 없는 방법들이다.

## 8. 적용하지 않은 절감 방법 (성능 영향 있음)

| 방법 | 예상 효과 | 위험 |
|---|---|---|
| 1단계(본문만)·2~3단계(라벨) 분리 | 요약 전송 약 40% 감소 | 품질 영향 적음. 구현 복잡도 증가 |
| 1단계를 Haiku·낮은 추론 강도로 | 큼 | "전체 내용 기준" 같은 경계 판단이 흔들림 |
| 코드 사전 필터(짧은 조각·한글 비율 낮은 조각 최대 436건) | 약 11% | 숫자 위주 실측표를 잘못 거를 수 있음 |
| 묶음 크기 40건 이상 | 고정 비용 약 10% 감소 | 대화가 길어져 판정 품질 저하 가능 |

- 정답 표본이 생기면 각 방법의 정확도 하락폭을 `/pilot`으로 재고 적용 여부를 정한다.

## 10. 프로젝트 구조

```
heritage-autoreview/
├─ CLAUDE.md                    세션마다 읽히는 짧은 규칙
├─ .claude/
│  ├─ agents/text-reviewer.md   검수 에이전트 (Sonnet, medium, Read·Write)
│  ├─ commands/pilot.md         /pilot   실험 가동
│  ├─ commands/review.md        /review  실제 검수
│  ├─ commands/resume-run.md    /resume-run 이어하기
│  └─ settings.json             권한: upload.py 실행 금지, .env 읽기 금지, 지침 수정 시 확인
├─ docs/
│  ├─ 총정리.md                  이 문서
│  ├─ supervisor.md             감독 절차
│  ├─ review_guide.md           판정 기준 (v4)
│  └─ pilot_history/            claude.ai에서 돌린 시범 기록(1·2차 결과, 표본, 비교표)
├─ scripts/
│  ├─ common.py                 사이트 클라이언트, 규칙 검사, 형식 정의
│  ├─ prepare.py                조회 → 규칙 검사 → 묶음 파일 (pilot / review)
│  ├─ validate.py               결과 검증 (누락·형식·사유 목록)
│  ├─ report.py                 집계 → report.md, results.csv (pilot이면 일치율)
│  └─ upload.py                 사이트 저장 (사람 전용, 기본 미리보기, --execute 시 확인 문구)
├─ data/gold.example.tsv        정답 표본 형식 예시
├─ runs/                        실행마다 폴더 생성 (git 제외)
├─ .env.example                 로그인 정보 템플릿
└─ requirements.txt             requests
```

- **실행 흐름**
  - `/pilot`: prepare.py pilot → text-reviewer 병렬 → validate.py → report.py(일치율)
  - `/review`: prepare.py review → text-reviewer 병렬 → validate.py → report.py → 사람이 upload.py
- **claude.ai 대화 방식과 다른 점**
  - 데이터는 브라우저 패널이 아니라 PC의 Python 스크립트가 로그인해서 받는다.
  - 데스크톱 앱이 필요 없다.

## 11. 알려진 한계·확인 필요

1. 사이트와 통신하는 부분(로그인, 목록, 라벨 조회, 저장)은 claude.ai 작업 공간에서 사이트 접속이 막혀 실행해 보지 못했다.
   - 첫 실행은 `python scripts/prepare.py pilot --source human --n 4` 처럼 작게 시험한다.
   - 로그인 실패 시 `.env`에 `HERITAGE_COOKIE`를 넣는 방식으로 바꾼다.
2. 검수 에이전트 정의의 `effort: medium`은 claude.ai 대화에서 적용된 것을 확인했다. CLI 버전에 따라 다를 수 있다.
3. 정답 표본이 없다. 사람 판정은 기준이 달라 정확도 측정이 안 된다(4장).
4. 자동 판정을 사람 판정(by: human)으로 저장하는 것, 생성·검증 모델 분리 원칙 모두 팀 확인 전이다.
